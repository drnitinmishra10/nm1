CONFERENCE RESEARCH PAPER · SECURITY OF GENERATIVE AI AND LARGE LANGUAGE MODELS

Beyond Effective Prompts: A Security-Centric Review of Threats in Prompt Engineering for Large Language Models

Dr. Nitin Mishra1, Dr. Rohit1
1Department of Computer Science and Engineering, Parul University, Vadodara, Gujarat, India
Corresponding author: Dr. Nitin Mishra · Professor, Department of Computer Science and Engineering, Parul University
Abstract— Prompt engineering has moved from being a practical technique for obtaining better responses from large language models (LLMs) to becoming an important part of the security boundary of AI-enabled applications. A well-designed prompt can improve accuracy, consistency, and task alignment; the same mechanism can also be manipulated to bypass controls, expose confidential information, or redirect an AI agent toward actions that were never intended by the system designer. This paper presents a structured, research-oriented review of security threats associated with prompt engineering and prompt-driven LLM applications. Drawing on recent academic literature, major conference studies, and the OWASP Top 10 for LLM and Generative AI Applications (2025), the paper consolidates sixteen closely related threats into a security taxonomy covering prompt manipulation, information exposure, model and data integrity, application and agent security, retrieval security, multimodal attacks, and resource exhaustion. Particular attention is given to prompt injection, indirect prompt injection, jailbreaking, system prompt leakage, sensitive information disclosure, instruction-hierarchy manipulation, excessive agency, vector and embedding weaknesses, and multimodal prompt injection. The discussion argues that prompt security cannot be achieved by adding stronger wording to a system prompt alone. Security controls must instead be distributed across the application architecture, with trust boundaries, authorization, input and output validation, least privilege, retrieval controls, monitoring, and adversarial evaluation. The paper concludes with a future-work agenda for measurable prompt robustness, adaptive defense, agent security, multilingual and code-switched attacks, multimodal protection, and reproducible benchmarks. The central message is straightforward: prompt engineering should be treated as a security-sensitive design activity rather than only a method for improving model performance.
Keywords— Prompt engineering, prompt injection, indirect prompt injection, jailbreak, LLM security, generative AI security, prompt leakage, AI agents, RAG, adversarial prompting.

1. Introduction

Large language models are now used as conversational assistants, coding partners, retrieval interfaces, document analysts, workflow agents, and decision-support components. In each of these settings, the prompt is more than a text string. It is part of the mechanism by which the application defines a task, establishes priorities, supplies context, and asks the model to produce an output. The security implication is important: when a model cannot reliably distinguish trusted instructions from untrusted content, the prompt itself becomes an attack surface.

Recent research has made this issue difficult to dismiss as a purely hypothetical concern. Zhan et al. introduced InjecAgent to evaluate indirect prompt injections against tool-integrated LLM agents and reported that, in their benchmark, ReAct-prompted GPT-4 agents were vulnerable to attacks in 24% of test cases [3]. AgentDojo similarly constructed realistic tasks involving email, banking, travel, and other tools to evaluate whether external data could manipulate agent behaviour [4]. These studies are particularly relevant because modern AI systems increasingly operate beyond a simple question-and-answer setting.

A second line of work studies attacks on the prompt and instruction structure itself. Wallace et al. argued that LLMs often fail because they do not reliably distinguish privileged instructions from untrusted user or third-party text, motivating the idea of an instruction hierarchy [5]. Xia et al. placed prompt leakage and prompt jailbreaks within a broader “prompt threat” perspective and emphasized the need to study both threats to prompts and threats created by malicious prompts [2].

Industry guidance also reflects this shift. The OWASP 2025 taxonomy identifies prompt injection, sensitive information disclosure, supply-chain vulnerabilities, data and model poisoning, improper output handling, excessive agency, system prompt leakage, vector and embedding weaknesses, misinformation, and unbounded consumption as major LLM application risks [1]. This taxonomy is useful for practitioners, but prompt engineering research requires a more granular view because some of the threats above arise specifically from instruction manipulation and context control.

2. Research Motivation and Objectives

Prompt engineering is often discussed in terms of effectiveness: clarity, specificity, decomposition, examples, role prompting, chain-of-thought alternatives, retrieval context, and output formatting. Security introduces a second question: “What happens when the prompt, the context, or the model output is intentionally manipulated?” The literature suggests that performance-oriented prompt design and security-oriented prompt design cannot be treated as completely separate activities [1], [2], [15].

This paper therefore has four objectives:

  1. To consolidate major prompt-related and prompt-adjacent security threats into a single conference-ready taxonomy.
  2. To distinguish direct prompt attacks from attacks that enter through retrieved data, tools, agents, embeddings, or multimodal content.
  3. To identify common architectural weaknesses that allow a prompt-level manipulation to become a system-level security incident.
  4. To define future research directions that can support measurable, reproducible, and deployment-oriented prompt security.
Research position. The key security issue is not that an LLM “understands language incorrectly” in an ordinary sense; rather, natural language can carry both legitimate instructions and untrusted content, while the application may give the model enough authority to turn a textual manipulation into a real-world action.

2. LITERATURE REVIEW AND TAXONOMY

3. Literature Review

The literature on LLM security has developed along several connected tracks. Early work demonstrated that language models can memorize and reveal portions of their training data [9]. Later research showed that alignment and safety behaviour can be bypassed through adversarial prompts [6], [7]. With the emergence of tool-using agents and retrieval-augmented generation (RAG), the attack surface expanded: the model began processing email content, web pages, retrieved passages, tool outputs, and multimodal inputs that may not be under the control of the application developer [3], [4].

OWASP provides the most practical industry-oriented consolidation for application developers [1]. The 2025 list deliberately separates prompt injection from system prompt leakage, vector weaknesses, excessive agency, and unbounded consumption. This separation is useful because a prompt can be the initial attack vector while the final harm occurs elsewhere. For example, a malicious instruction may cause an agent to call a privileged tool; the technical failure is therefore not limited to the prompt itself.

Academic work also indicates that defenses should not rely only on one additional instruction appended to the system prompt. Chen et al. explored a defense approach that leverages attack techniques to reinforce the intended instruction and reported improvements across their experimental settings [11]. Xiong et al. proposed a defensive prompt patch for jailbreak attacks and emphasized the practical need to balance security and utility [12]. These results are useful, but they do not eliminate the architectural lesson that authorization and privilege boundaries should remain outside the LLM.

The emerging multimodal literature makes the problem wider still. Yeo and Choi evaluated direct, indirect, image-based, and leakage-oriented attacks across commercial models [13]. More recent work has demonstrated image-based prompt injection as a black-box attack against multimodal LLMs, showing that instructions may be hidden inside visual inputs rather than typed by a user [14]. For security engineering, this means that “prompt” should be interpreted broadly as the complete instruction-bearing context presented to the model.

4. Proposed Security Taxonomy

Based on the literature, this paper organizes threats into five layers. The first layer contains prompt manipulation attacks, where the primary objective is to alter instruction following. The second covers information security, where attackers seek secrets, prompts, or protected data. The third concerns model and knowledge integrity, including poisoned training or retrieval data. The fourth covers application and agent execution, where model output becomes an action in another system. The fifth covers availability and multimodal surfaces, including resource exhaustion and attacks hidden in non-text inputs.

5. THREAT ANALYSIS — PROMPT, INFORMATION, AND MODEL INTEGRITY

5.1 Prompt Manipulation Threats

1) Prompt Injection

Prompt injection is the foundational threat in which an attacker places instructions into input that compete with the application’s intended instructions. The attack does not require a software exploit in the conventional sense; instead, it abuses the model’s ability to interpret natural language as a command. A simple user-facing chatbot may therefore be manipulated through a carefully worded message, while an agent can be manipulated through an instruction that causes a tool call. The security challenge is fundamentally one of trust separation.

2) Indirect Prompt Injection

Indirect injection becomes more serious when the attacker does not directly control the user’s query. Malicious text can be inserted into a public webpage, an email, a shared document, or another source that the AI later retrieves. InjecAgent specifically studied this setting and found practical weaknesses in tool-integrated agents [3]. AgentDojo further demonstrated that real-world tasks become security tests once an agent is required to act on information obtained from external tools [4].

This threat deserves special attention in RAG systems because the retrieval layer creates a trusted-looking context window. A document may be relevant to the question but still be untrusted as an instruction source. Mixing these two roles—knowledge and authority—is one of the recurring design errors in prompt-driven applications.

3) Jailbreaking

Jailbreaking refers to attempts to circumvent safety behaviour through adversarial prompt construction. Wei et al. studied how safety training can fail under different jailbreak patterns [6], while Zou et al. demonstrated automated adversarial suffixes that could transfer across multiple aligned models and interfaces [7]. In practice, jailbreaks can include role-play framing, instruction conflicts, obfuscation, multilingual phrasing, long-context manipulation, or adversarially generated prompt components.

From a prompt-engineering perspective, jailbreak research demonstrates a deeper point: stronger instruction wording is not equivalent to stronger security. An application that depends exclusively on a model refusing unsafe requests has a weaker security boundary than one that independently enforces permissions and actions.

4) Instruction Hierarchy Manipulation

Modern applications often contain multiple instruction levels: a system message, developer rules, user input, retrieved context, and tool-generated content. An attacker can exploit ambiguity about which instruction is authoritative. Wallace et al. proposed explicit instruction hierarchy training so that higher-priority instructions dominate lower-priority ones during conflicts [5]. This work provides a useful conceptual foundation for secure prompt construction, although model-side hierarchy training should be paired with external enforcement.

5) Context Hijacking

Context hijacking occurs when attacker-controlled information becomes part of the conversation or retrieved context and then influences later decisions. The attack can be persistent across multi-step tasks because the compromised context is repeatedly fed back to the model. In agent workflows, this can create an attack chain rather than a single malicious response [4]. Context should therefore be treated as data with provenance, not automatically as policy.

5.2 Information Security Threats

6) System Prompt Leakage

System prompt leakage is the deliberate extraction of hidden instructions. Recent work has shown that system prompts can be an explicit target of extraction attacks [8]. OWASP also makes an important distinction: the system prompt itself should not be treated as a secret or a security control; the real risk arises when secrets, permission logic, connection information, or critical guardrails are placed there [1]. In other words, a leaked prompt may be a symptom of weak architecture rather than the complete vulnerability.

7) Sensitive Information Disclosure

Sensitive information may enter an LLM through user prompts, retrieved documents, conversation history, logs, fine-tuning data, or external tools. Carlini et al. demonstrated that language models can sometimes reproduce memorized training examples, including personally identifiable information and other sequences [9]. In enterprise systems, the risk is broader because confidential information can also be exposed through poorly designed retrieval or tool access.

8) Prompt-Based Data Exfiltration

Data exfiltration is an outcome-oriented threat in which prompt manipulation is used to make an application retrieve, combine, transform, or transmit protected information. The attacker may not need direct database access; instead, the model becomes an intermediary between a privileged data source and an attacker-controlled instruction. InjecAgent explicitly includes private-data exfiltration among its attack intentions [3]. Preventing this class of attack requires permission-aware retrieval and tool authorization, not only prompt wording.

5. THREAT ANALYSIS — APPLICATION, RAG, SUPPLY CHAIN, AND AVAILABILITY

5.3 Model and Knowledge Integrity

9) Data and Model Poisoning

Data and model poisoning occurs when malicious or manipulated content is introduced into training, fine-tuning, embeddings, or other knowledge sources. A related line of research has shown that backdoor-like behaviours can persist despite standard safety training in controlled experiments [10]. For prompt engineering, the lesson is important because prompt quality cannot compensate for compromised data foundations.

10) Vector and Embedding Weaknesses

RAG systems rely on embeddings and vector databases to select context. OWASP identifies risks including unauthorized access, cross-context information leakage, embedding inversion, and poisoned retrieval data [1]. A prompt may be perfectly written yet still lead to an unsafe response because the wrong document was retrieved or because a malicious document was ranked highly. Security therefore needs to extend from prompt construction into retrieval and access-control design.

11) Supply-Chain Vulnerabilities

LLM applications rarely consist of a single model. They may use external models, model adapters, prompt templates, plugins, libraries, vector stores, APIs, safety filters, and datasets. A weakness or compromise in any component can propagate into the final application [1]. Supply-chain security is especially relevant to prompt engineering because teams often reuse public prompt templates, agent frameworks, and third-party tool connectors without applying the same security scrutiny used for conventional software dependencies.

5.4 Application and Agent Security

12) Improper Output Handling

A model output is text, but downstream software may interpret that text as HTML, JavaScript, SQL, shell commands, file paths, or API parameters. OWASP warns that insufficient validation and sanitization can turn model output into XSS, SQL injection, SSRF, privilege escalation, or remote code execution pathways [1]. This threat shows why secure prompting and secure software engineering must be integrated: the prompt may shape the output, but the application decides whether that output receives executable authority.

13) Excessive Agency

Agentic systems can read files, send emails, modify records, access repositories, call APIs, or initiate workflows. OWASP describes excessive agency in terms of excessive functionality, excessive permissions, and excessive autonomy [1]. A prompt injection becomes materially more dangerous when the model has broad capabilities. The principle of least privilege therefore applies to AI agents just as it applies to users and service accounts.

For example, an assistant that only needs to read a document should not automatically receive permission to delete or modify it. A model should propose sensitive actions, while deterministic application logic should validate authorization, target, and scope before execution.

5.5 Availability and Reliability Threats

14) Unbounded Consumption

Unbounded consumption refers to uncontrolled or excessive use of model inference resources. OWASP identifies denial of service, economic loss, service degradation, and model-theft-related risks under this category [1]. Long prompts, repeated requests, expensive tool loops, or uncontrolled agent recursion can all increase resource consumption. Prompt engineering should therefore include token budgets, rate limits, loop limits, timeouts, and anomaly detection where appropriate.

15) Instruction-Induced Misinformation

LLMs can generate confident but false statements, and prompt design can amplify this behaviour by demanding unsupported certainty, forcing a predetermined conclusion, or discouraging appropriate uncertainty. OWASP treats misinformation as a distinct application risk because downstream reliance can produce operational, reputational, or safety consequences [1]. From a research perspective, evaluation should therefore measure not only attack success but also whether defensive prompts preserve factual reliability.

5.6 Multimodal and Emerging Threats

16) Multimodal Prompt Injection

Multimodal systems add images, screenshots, scanned documents, and other visual inputs to the instruction channel. Yeo and Choi evaluated image-based injection together with direct, indirect, and leakage attacks [13]. Nagaraja et al. later demonstrated image-based prompt injection against multimodal LLMs in a black-box setting and reported that adversarial instructions could be embedded visually [14]. This matters because a human viewer may regard an image as harmless while the model's vision-language pipeline interprets its hidden or low-salience text as an instruction.

Key architectural observation. Across these threats, the prompt is often the entry point, but the impact is determined by the surrounding system. A prompt injection against a read-only summarizer may be inconvenient; the same injection against an agent with email, file, database, or payment permissions can become a confidentiality or integrity incident.

7. DISCUSSION, RESEARCH GAPS, AND FUTURE WORK

7. Discussion

The reviewed evidence supports a simple but significant conclusion: prompt security is a systems problem. Prompt injection is often discussed as though the model only needs a better instruction such as “ignore malicious commands.” That approach can be helpful as one layer, but it is not a complete security mechanism. OWASP explicitly recommends that sensitive authorization decisions and privilege boundaries not be delegated to the LLM [1]. Academic studies of agents reinforce the same point because tool access converts language-level manipulation into external actions [3], [4].

A second observation concerns trust boundaries. In conventional software security, data and instructions are normally distinguished by type and interface. In LLM applications, both may be represented as natural language. A retrieved paragraph can look identical to a policy instruction inside the context window. This “instruction-data dual use” makes prompt security fundamentally different from conventional input validation.

Third, prompt attacks are becoming increasingly adaptive. Jailbreak research has moved from manually designed prompts toward automatically generated attacks [7]. Prompt injection research is also producing benchmark-driven attack and defense methods [3], [11]. Therefore, a static list of blocked phrases or a single defensive prompt is unlikely to remain sufficient as attackers adapt.

Finally, security and usability remain coupled. Stronger filtering can reduce attack success but may also reduce legitimate task completion. Recent defensive studies explicitly evaluate this trade-off [11], [12]. The objective should consequently be robust task alignment: the model should perform the authorized task, ignore untrusted instructions, and stop or escalate when authority is unclear.

8. Research Gaps

8.1 Lack of a Unified Prompt-Security Evaluation Protocol

Existing benchmarks measure different aspects: jailbreak resistance, indirect injection, prompt leakage, agent tool safety, or output reliability. A common evaluation protocol could report attack success, task completion, confidential-data exposure, unauthorized-action rate, utility degradation, and resource consumption together. Such a benchmark would make defenses more comparable across models and application designs.

8.2 Multilingual and Code-Switched Prompt Attacks

A large portion of benchmark material is English-centric. Real deployments, especially in linguistically diverse environments, may contain Hindi-English code-switching, regional-language prompts, transliterated text, mixed scripts, and multilingual retrieved documents. Security research should test whether instruction hierarchy and injection defenses remain stable when the attacker changes language or script while preserving the malicious intent.

8.3 Security of Long-Context Systems

Long context windows allow more information to be processed, but they also provide more space for hidden, repeated, or strategically placed instructions. Research is needed on whether position, repetition, recency, and context compression change attack success. A practical defense should work not only on short prompts but also on long enterprise documents and multi-turn agent histories.

8.4 Agent-Specific Security Metrics

Traditional LLM evaluation often measures response accuracy. An agent requires additional measures: unauthorized tool calls, unauthorized data access, irreversible actions, action-chain length, and recovery after an unsafe intermediate step. AgentDojo provides an important direction, but further domain-specific benchmarks are required [4].

8.5 Multimodal Security and Cross-Modal Attacks

Image-based injection demonstrates that the attack surface is no longer confined to text [14]. Future work should test screenshots, PDFs, charts, handwritten content, diagrams, hidden text, metadata, and combinations of visual and textual instructions. Defenses should also preserve accessibility and legitimate document understanding rather than simply discarding unusual visual content.

8.6 Provenance-Aware Prompt Construction

RAG systems should carry source information through the entire reasoning and tool pipeline. A useful research direction is to attach provenance and trust labels to each context item and evaluate whether models can consistently treat “information to read” differently from “instructions to follow.” This aligns with the instruction-hierarchy perspective [5] and with RAG-specific security concerns identified by OWASP [1].

9. Future Work

The future research agenda proposed in this paper is organized around robustness, transferability, reliability, and enforceability. First, robustness studies should evaluate attacks under paraphrasing, multilingual transformation, context reordering, and model changes. Second, transferability research should determine whether attacks and defenses generalize across closed and open models rather than working only on a single benchmark configuration.

Third, reliability should be measured jointly with security. A defense that blocks every uncertain request is not necessarily useful. A more meaningful metric is secure task success: the proportion of legitimate tasks completed correctly while malicious or unauthorized actions are consistently rejected. Fourth, enforceability should move beyond model instructions toward deterministic controls: policy engines, permission checks, tool schemas, sandboxing, data-loss prevention, and human approval for high-impact actions.

An especially important future direction is the development of adaptive prompt-security gateways. Such a gateway could classify content by trust level, detect instruction conflicts, inspect retrieved documents, constrain tool permissions, and evaluate the model’s output before execution. The objective is not to replace the LLM with rigid rules, but to place the LLM inside a broader security architecture where every high-risk action has an independent validation path.

10. CONCLUSION AND REFERENCES

10. Conclusion

Prompt engineering has become an essential practical skill for obtaining reliable behaviour from large language models, but its security implications now deserve equal attention. The review in this paper shows that prompt-related threats extend well beyond the familiar idea of a malicious user typing an “ignore previous instructions” message. Attacks can enter through direct prompts, external documents, retrieved content, system-prompt extraction attempts, multimodal inputs, poisoned knowledge sources, and compromised third-party components. Once an AI system is connected to tools, databases, files, or business workflows, the consequences can move from incorrect text generation to confidentiality loss, privilege misuse, unauthorized transactions, and service degradation.

The sixteen threats consolidated here provide a practical research map: prompt injection, indirect prompt injection, jailbreaking, instruction hierarchy manipulation, context hijacking, system prompt leakage, sensitive information disclosure, prompt-based data exfiltration, data and model poisoning, vector and embedding weaknesses, supply-chain vulnerabilities, improper output handling, excessive agency, unbounded consumption, instruction-induced misinformation, and multimodal prompt injection. Several of these are formally recognized by OWASP; others are finer-grained research categories derived from the academic literature and are best understood as attack patterns or outcomes that can overlap with the OWASP categories [1], [2].

For future prompt-engineering research, the practical principle is clear. Security should not be achieved by “better wording” alone. A secure application should distinguish trusted instructions from untrusted context, protect secrets outside the prompt, enforce authorization independently, limit agent permissions, validate outputs before execution, control retrieval sources, and continuously test the system using adaptive adversarial benchmarks. This layered approach is especially important in educational institutions, enterprise systems, healthcare, finance, and public-service applications where the cost of an unintended AI action may be considerably higher than the cost of an incorrect conversational answer.

In conclusion, the research community should treat prompt engineering as both a communication mechanism and a security interface. The next generation of prompt-security work should therefore aim for measurable robustness, multilingual and multimodal resilience, reproducibility across models, and architectural enforceability. The most useful prompt is not simply the one that produces a good answer; it is the one that remains aligned with the authorized task even when the surrounding information is adversarial.
